# Studio Atelier Frontend Style Guide

**Product:** Art Community Information System & Portfolio Platform  
**Visual direction:** Studio Atelier / Warm Obsidian & Gallery Amber  
**Status:** Approved visual foundation  
**Audience:** Frontend engineers, product designers, and implementation agents  
**Primary stack:** Tailwind CSS v4 (CSS-first tokens), shadcn/ui, Lucide Icons  
**Primary locale:** Bahasa Indonesia, with familiar English art and technical terms where clearer  
**Time display:** Asia/Makassar — WITA (UTC+8)

---

## 1. Design Thesis

> **Artwork is the hero; the interface is the gallery lighting.**

The platform must feel like an exclusive digital atelier rather than a generic SaaS dashboard. The interface should frame artwork, preserve color fidelity, and make community activities feel curated and intentional. UI chrome must remain restrained: fewer visible controls, low-contrast surfaces, subtle borders, and carefully placed amber highlights.

The visual experience should communicate four qualities:

1. **Immersive:** the dark warm canvas lets artwork dominate the viewport.
2. **Refined:** spacing, typography, and alignment feel deliberate rather than decorative.
3. **Tactile:** voting, zooming, opening drawers, and changing commission status provide clear physical feedback.
4. **Trustworthy:** permissions, deadlines, Stars, voting states, and destructive actions are always understandable.

This is not a neon gaming interface, a crypto dashboard, or a black-and-gold luxury template. Amber is a functional light source and semantic accent—not a decorative color applied everywhere.

### Technology relationship: Tailwind CSS and shadcn/ui

**Tailwind CSS and shadcn/ui do not conflict. They are complementary layers.**

- **Tailwind CSS v4** is the styling engine and token layer. It controls color, typography, spacing, responsive behavior, state variants, and layout utilities.
- **shadcn/ui** provides accessible component source code and interaction patterns that are copied into the project and then styled with Tailwind utilities and the project's CSS variables.
- **Radix primitives**, where used by shadcn/ui components, provide accessible behavior for dialogs, menus, tooltips, tabs, sheets, and similar controls.
- **Lucide** is the single icon system used by both the custom product UI and shadcn-derived components.

Use shadcn/ui's **New York** visual baseline for new components because it is the current default and closer to the compact, refined atelier direction. Treat it only as a starting structure: every component must consume the Studio Atelier tokens and must not retain generic demo styling.

Recommended project conventions:

- Tailwind CSS v4 with CSS-first configuration.
- `@theme inline` mappings for semantic design tokens.
- shadcn/ui initialized with CSS variables enabled.
- Neutral base color, then replace the generated neutral values with the warm obsidian system.
- New York component style.
- Lucide as the icon library.
- `tw-animate-css` for shadcn-compatible utility animation where needed; product-specific tactile interactions may use a small motion library only when CSS is insufficient.
- A shared `cn()` helper for merging conditional Tailwind classes.
- Component variants managed consistently, preferably with the variant approach already generated by shadcn/ui rather than inventing a second styling API.

Do not install another full component design system such as Material UI, Ant Design, or Chakra alongside this stack. That would introduce conflicting spacing, theming, and accessibility conventions. Purpose-built gallery components—pan/zoom viewer, media player, masonry layout—may be added when they solve a specialized need and are visually adapted to the same tokens.

## 2. Core Experience Principles

### 2.1 Artwork-first hierarchy

- Artwork should usually occupy the largest visual area on gallery, challenge, portfolio, and jury screens.
- Navigation, metadata, and controls should support inspection without competing with the image.
- Avoid colorful UI elements beside artwork. Most interface elements use neutral charcoal, warm white, and muted gray.
- Do not place strong gradients, thick borders, or multiple bright badges around artwork.
- In evaluation contexts, preserve the original aspect ratio and avoid decorative crops.

### 2.2 Progressive disclosure

- Show the most important action and state first.
- Secondary metadata belongs in hover layers, expandable panels, drawers, tooltips, or a collapsible side panel.
- Advanced controls should not be permanently visible when the user is only browsing.
- Mobile views should prioritize artwork, title, artist, primary action, and current state. Less important metadata moves below or into a drawer.

### 2.3 Atmospheric, not low-contrast

- Dark atmospheric styling must not sacrifice readability.
- Primary text must have strong contrast against the canvas and surfaces.
- Muted text is reserved for metadata and supporting explanations, never critical instructions.
- Borders may be subtle, but interactive boundaries must remain discoverable through shape, spacing, hover, and focus treatment.

### 2.4 One amber focal point per region

- Amber indicates the current primary action, selected state, Stars, award status, active challenge stage, or jury decision.
- A component region should normally have only one dominant amber element.
- If everything is amber, hierarchy has failed.

### 2.5 Fairness must be visible

- Challenge voting should communicate that every candidate has equal prominence.
- Users must understand which candidates they have viewed, which have Stars, and how many Stars remain.
- The interface must not imply that the first card is the best card.
- Ranking visuals are not shown before the product rules allow them.

## 3. Visual Foundation

## 3.1 Color system

### Primary dark theme

| Token | Value | Intended use |
|---|---:|---|
| `canvas` | `#0E1015` | Main page background and full-screen gallery canvas |
| `canvas-elevated` | `#13161D` | Sticky navigation and large background sections |
| `surface-1` | `#191C23` | Cards, panels, sidebars, and form groups |
| `surface-2` | `#20232C` | Elevated controls, hover surfaces, nested panels |
| `surface-3` | `#292D37` | Selected neutral surfaces and strong hover states |
| `text-primary` | `#F6F2E9` | Main headings and body text |
| `text-secondary` | `#B7B5AF` | Supporting copy and secondary labels |
| `text-muted` | `#7E818B` | Metadata, timestamps, disabled labels |
| `amber-500` | `#F59E0B` | Primary accent, Stars, active stage, selected item |
| `amber-400` | `#F8B84E` | Hover and glow highlight |
| `amber-300` | `#F8CA79` | Subtle icon or text highlight on dark surfaces |
| `border-subtle` | `rgba(255,255,255,0.10)` | Default 1px hairline |
| `border-strong` | `rgba(255,255,255,0.18)` | Hover, selected-neutral, and panel boundaries |
| `glass-fill` | `rgba(20,23,30,0.72)` | Floating capsules, sticky bars, lightbox controls |

### Semantic colors

| State | Recommended color | Usage rule |
|---|---:|---|
| Success / Open | `#75C985` | Commission open, saved, completed step |
| Warning / Waitlist | `#E6A84A` | Waitlist, deadline warning, Stars remaining reminder |
| Error / Destructive | `#E26767` | Delete, disqualification, upload failure, invalid ballot |
| Information | `#6EA8E8` | Neutral system help and informational callouts |
| Paused / Neutral | `#9296A0` | Paused challenge, inactive state, unavailable action |

Semantic colors should remain slightly muted so they do not overpower artwork. Do not use pure green, red, blue, or yellow.

### Color behavior around artwork

- Artwork containers use neutral black or charcoal letterboxing.
- Do not tint artwork thumbnails with the amber brand color.
- Hover overlays use neutral black gradients rather than colored gradients.
- The public watermark may use warm white or neutral gray. It should not recolor the work.
- The master-quality member view must not add filters, contrast changes, or decorative overlays.

### Optional light gallery mode

If a light mode is implemented, it should feel like warm archival paper rather than pure white SaaS UI:

- Canvas: `#F3F0E9`
- Surface: `#FAF8F3`
- Elevated surface: `#FFFFFF`
- Primary text: `#17191E`
- Secondary text: `#5F6269`
- Border: `rgba(14,16,21,0.12)`
- Accent remains `#D98305` or another contrast-safe darkened amber.

Dark mode remains the default and the primary art direction. Light mode should reuse the same spacing, typography, and component hierarchy rather than becoming a separate design language.

## 3.2 Typography

### Font families

| Role | Typeface | Usage |
|---|---|---|
| Display | **Syne** | Hero copy, major section headings, featured artist names, challenge titles |
| Interface and body | **Plus Jakarta Sans** | Navigation, forms, cards, buttons, descriptions, comments |
| Technical metadata | **JetBrains Mono** | WITA timestamps, software tags, file details, ranks, IDs, token counts |

### Type hierarchy

- **Display XL:** 64–88px desktop, 44–56px mobile; Syne 700; tight line height around 0.95–1.02.
- **Display L:** 44–64px desktop, 34–44px mobile; Syne 650–700.
- **Heading 1:** 32–40px; Syne 650–700.
- **Heading 2:** 24–30px; Syne 600–700.
- **Heading 3 / card title:** 17–21px; Syne 600 or Plus Jakarta Sans 700 depending on context.
- **Body L:** 17–18px; Plus Jakarta Sans 400–500; line height 1.65.
- **Body:** 14–16px; Plus Jakarta Sans 400–500; line height 1.55–1.7.
- **UI label:** 12–14px; Plus Jakarta Sans 600–700.
- **Metadata:** 10–12px; JetBrains Mono 400–500; modest letter spacing.
- **Micro label:** 9–10px; JetBrains Mono 500; uppercase only for short labels.

### Typography rules

- Syne is expressive; do not use it for paragraphs, long instructions, tables, or dense forms.
- Avoid excessive uppercase. Uppercase is limited to status stamps, category labels, and short metadata.
- Use sentence case for buttons and form labels in Bahasa Indonesia.
- Keep body text line length near 55–75 characters.
- Do not use very thin font weights on dark backgrounds.
- Numeric values that need comparison—Stars, countdowns, dimensions, ranks—should use JetBrains Mono with tabular numerals.

## 3.3 Spacing and layout

Use an 8px base rhythm with 4px for micro-adjustments.

| Scale | Value | Typical use |
|---|---:|---|
| `1` | 4px | Icon alignment and micro gaps |
| `2` | 8px | Badge padding and compact gaps |
| `3` | 12px | Control gaps and compact card padding |
| `4` | 16px | Standard mobile padding and form gaps |
| `5` | 20px | Standard component padding |
| `6` | 24px | Card and panel padding |
| `8` | 32px | Section subdivisions |
| `10` | 40px | Large component separation |
| `12` | 48px | Section intro separation |
| `16` | 64px | Desktop section spacing |
| `24` | 96px | Major desktop section spacing |

### Page layout

- Desktop content maximum width: 1280–1440px depending on screen purpose.
- Reading content maximum width: 720–800px.
- General desktop page padding: 32–56px.
- Tablet page padding: 24–32px.
- Mobile page padding: 16–20px.
- Dense admin tables may extend wider but must preserve a fixed first column or responsive card fallback.

### Grid behavior

- Use 12-column layout for dashboard and desktop composition.
- Gallery columns are determined by available width and artwork needs, not by a fixed number everywhere.
- Candidate voting cards must use equal visual weight even when artwork ratios differ.
- Use consistent card heights or a framed internal canvas for the balanced voting grid; masonry is appropriate for discovery galleries but not for fairness-sensitive voting.

## 3.4 Shape, borders, and elevation

### Radii

- Large artwork frame or modal: 20–24px.
- Standard card and panel: 14–18px.
- Input and button: 10–12px.
- Floating capsule and status pill: fully rounded.
- Artwork itself may use 8–12px inside a larger framed container.

Do not make every component a floating rounded card. Larger page sections may use border lines and spacing without an enclosing container.

### Borders

- Default: 1px `border-white/10`.
- Hover: increase to approximately `border-white/20`.
- Selected: amber border or a 2px amber leading edge, but not both unless the state is critical.
- Focus: visible 2px amber focus ring with offset from the component.
- Avoid double borders and bright white outlines.

### Shadows and glow

- Use large, soft black shadows for elevated panels and lightboxes.
- Amber glow is reserved for Stars, selected winner states, and important active states.
- Never apply amber glow to every button or card.
- Glass components use backdrop blur only when content remains readable and performance is acceptable.

Recommended elevation language:

- Base card: hairline border, no shadow.
- Hovered interactive card: slight translate upward, stronger border, soft shadow.
- Floating action capsule: backdrop blur, dark glass fill, large soft shadow.
- Modal/lightbox: near-black scrim with a strong separation from the side panel.

---

## 3.5 Iconography

Use **Lucide Icons** consistently.

- Default icon size: 16–20px.
- Small metadata icon: 14–16px.
- Major empty-state icon: 32–40px inside a restrained container.
- Default stroke width should remain close to Lucide's standard; do not mix filled emoji, text letters, and outline icons.
- Every icon-only button requires an accessible label and tooltip on hover/focus.
- Icons support labels; they do not replace unclear wording.
- Stars may use the Lucide Star icon with filled amber state when allocated and outline state when available.

Avoid tiny decorative icons that do not communicate an action or status.

---

## 3.6 Motion and tactile feedback

Motion should feel like a well-made physical interface: controlled, quiet, and responsive.

### Timing

- Hover and color change: 140–180ms.
- Drawer and popover: 180–240ms.
- Modal and lightbox: 220–300ms.
- Large page transition: maximum 350ms.
- Star allocation spring: approximately 220–320ms, with restrained overshoot.

### Motion rules

- Artwork thumbnail hover may scale up by no more than 1.02–1.04.
- Cards may translate vertically by 1–3px on hover.
- Allocating a Star triggers a small scale-and-settle animation and immediately updates the budget.
- Removing a Star should be equally clear but less celebratory.
- Focus deck movement uses smooth directional sliding that preserves spatial orientation.
- Never animate layout unexpectedly while the user is comparing candidates.
- Respect `prefers-reduced-motion`; replace spring and slide effects with short opacity changes.

## 4. Component System

Use shadcn/ui as the accessible behavioral foundation, then restyle it to match the atelier language. Do not ship default shadcn visuals unchanged.

## 4.1 Navigation

### Global navigation

- Use a slim sticky header on desktop and a compact top bar on mobile.
- Background is translucent warm obsidian with blur and a bottom hairline.
- Primary sections: Beranda, Galeri, Challenge, Artist, and the authenticated user menu.
- The active item uses warm-white text and a restrained amber underline or dot.
- Avoid large filled navigation tabs.

### Mobile navigation

- Prefer a five-item bottom navigation for frequently used member areas if the information architecture supports it.
- The bottom bar must not cover voting controls or the ballot review dock.
- Admin and lower-frequency actions belong in the profile/menu drawer.

## 4.2 Buttons

### Primary button

- Amber fill, dark text, medium weight.
- Used once per action region for the main next action.
- Examples: `Kirim karya`, `Simpan pilihan`, `Hubungi via WhatsApp`.

### Secondary button

- Charcoal or transparent background with hairline border.
- Warm-white label; border strengthens on hover.

### Ghost button

- No container until hover.
- Suitable for lightweight toolbar actions.

### Destructive button

- Muted red text or outline by default; solid red only inside final confirmation.

Button labels should be verbs and explicit. Avoid vague text such as `Lanjut` when `Tinjau suara` or `Publikasikan hasil` is clearer.

## 4.3 Inputs and forms

- Input background: `surface-1` or transparent within an established panel.
- Default border: subtle hairline; active border and ring: amber.
- Labels remain visible above fields. Do not rely on placeholder-only forms.
- Supporting text appears below the input in muted text.
- Validation appears close to the relevant field and includes readable text, not color alone.
- Upload zones should clearly state accepted formats, maximum file size, and privacy level.
- Artwork upload preview must show whether the user is viewing the original or public derivative.

## 4.4 Cards

Cards should exist only when grouping helps comprehension.

- Artwork card: image-dominant, minimal lower metadata, neutral hover overlay.
- Service card: thumbnail, service name, price starting point, turnaround, and clear CTA.
- Challenge card: banner, status, deadline, enabled winner systems, and primary action.
- Dashboard metric card: compact and low contrast; avoid colorful SaaS card grids.

## 4.5 Badges and status pills

- Use pills for compact states such as `OPEN`, `WAITLIST`, `CLOSED`, `VOTING`, or `JURI`.
- Use a small semantic dot plus text for commission status.
- Amber badges are reserved for Stars, awards, jury designation, and active challenge stages.
- Status text must remain understandable without relying on color.

## 4.6 Drawers, dialogs, and side panels

- Use a right-side panel for lightbox comments and technical metadata on desktop.
- On mobile, side panels become bottom sheets or stacked content below the artwork.
- Confirmation dialogs must state the consequence and whether the action can be undone.
- The ballot review dock may expand into a drawer without navigating away from candidates.

## 4.7 Feedback states

- Toasts confirm temporary outcomes such as `Draf tersimpan`.
- Inline status should confirm persistent outcomes such as ballot submission or upload processing.
- Skeleton loaders should mirror final image frames and text blocks.
- Empty states should explain what is missing and provide a relevant next action.
- Errors must preserve user input and explain recovery.

## 5. Artwork Presentation Rules

## 5.1 Public guest view

- Guests do not have an account or session.
- Public artwork uses the watermarked derivative with stripped metadata and limited resolution.
- The interface may show a subtle `Versi publik · Watermarked` indicator.
- Do not present a fake security toggle suggesting that guests can reveal the master file.
- Disable casual dragging and context-menu access only as lightweight friction, never as a claim of complete protection.

## 5.2 Authenticated member view

- Members may access the full-quality master when authorized.
- Clearly distinguish `Master quality` from `Public preview` in the lightbox.
- The member view does not need metadata stripping for challenge evaluation.
- Access to the original must still be enforced by authorization, not by a hidden frontend URL.

## 5.3 Gallery masonry

- Use masonry for public showcase and personal portfolio discovery.
- Preserve native aspect ratios and avoid awkward center cropping.
- Hover or tap reveal includes artwork title, artist, and media type.
- GIF and video entries show an unambiguous motion/media indicator.
- Autoplay video only when muted and visible, and stop playback when offscreen.

## 5.4 Lightbox

- Static artwork supports full-screen pan and zoom.
- The canvas is neutral near-black with no ambient color cast.
- Desktop uses an optional collapsible side panel for description, software tags, comments, and critique.
- Mobile prioritizes the artwork; details move below or into a sheet.
- Zoom controls, current zoom level, reset, close, and panel toggle remain keyboard accessible.
- The user should be able to close with Escape and navigate with arrow keys when applicable.

## 6. Challenge Candidate Display and Voting Fairness

This section is a product rule as well as a visual rule. The candidate presentation must remain fair for challenges with approximately 8 to 20+ submissions.

## 6.1 Deterministic per-voter ordering

- Generate a deterministic candidate order using the challenge and voter/session identity.
- The same voter should see a stable order during the same voting round, preventing cards from unexpectedly moving after they begin evaluating.
- Different voters receive different orders so no candidate permanently receives the first or last position.
- Filtering, changing view mode, reopening the ballot, or refreshing must not silently produce a new order for the same voter and round.
- The frontend receives an already authorized ordering seed or ordered candidate list. Do not expose sensitive internal identifiers unnecessarily.
- Never visually label early positions as more important.

## 6.2 Dual discovery view A: Balanced Atelier Grid

The grid is the scanning and discovery mode.

### Card composition

- Every candidate card receives equal outer dimensions and visual weight.
- Artwork sits inside a neutral framed canvas using `object-contain` for evaluation, with restrained letterboxing when ratios differ.
- The card displays candidate number/index, title, artist name, media type, and current anonymous total Stars if the product rules allow it.
- Artist names and artwork remain visible. What remains private is the identity of voters and their allocation.
- Star allocation controls occupy the same position on every card.
- Do not use masonry in the voting grid because different card heights create unequal prominence.

### Grid density

- Large desktop: normally 3–4 columns.
- Standard desktop/tablet landscape: 3 columns.
- Tablet portrait: 2 columns.
- Mobile: 1 column or a controlled horizontal candidate rail only when accompanied by an explicit index.
- The user must not lose their place when opening and closing a candidate.

### Quick jump index

- Provide a compact index showing all candidates as numbered nodes or miniature neutral thumbnails.
- States: unviewed, viewed, has Stars, and disqualified/unavailable.
- The index is navigation, not ranking.
- Selecting an index item scrolls to the candidate and moves keyboard focus appropriately.

## 6.3 Dual discovery view B: Focus and Comparison Deck

The focus deck is the careful evaluation mode.

### Focus mode

- One candidate dominates the screen with maximum artwork area.
- Navigation supports previous/next buttons, keyboard arrows, swipe on touch, and direct candidate index selection.
- Show position as `Karya 07 dari 18`, never as a rank.
- Star controls and current allocation remain accessible without covering important artwork content.
- Preserve the same deterministic order used by the grid.
- Mark a candidate as viewed only after a meaningful exposure threshold, not immediately on incidental rendering.

### Comparison mode

- Users may pin two candidates for side-by-side comparison.
- Both canvases receive identical dimensions and zoom rules.
- Metadata rows align to make title, artist, medium, software, and allocated Stars easy to compare.
- Independent zoom is the default; optional synchronized zoom may be offered when useful.
- Comparison does not change candidate order or allocation.
- On narrow screens, use a deliberate A/B toggle or vertical comparison rather than squeezing two unreadable images side by side.

## 6.4 Stars interaction model

- `Stars` are vote units. A member may allocate up to two Stars to one submission if allowed by the challenge configuration.
- Members may leave Stars unused.
- Members may change their ballot while the challenge remains in the Voting state.
- Members may vote even if they did not submit an artwork.
- Moderators and assigned jurors may participate in community voting because jury selection is a separate winner mechanism.
- The control should show allocation clearly, for example an outline Star button plus `0 / 2`, `1 / 2`, or `2 / 2`.
- Adding a Star provides a short spring response, updates the remaining budget immediately, and announces the change to assistive technology.
- Removing a Star is always available during Voting unless the submission becomes unavailable.
- Preventing self-voting must be communicated directly on the member's own submission with disabled control and explanation.

## 6.5 Anonymous vote visibility

- Artwork titles and artist names are visible during voting.
- Real-time total Stars may be visible according to the approved business rule.
- Member-facing screens never reveal who voted for whom.
- Admin/moderator auditing views may access voter allocation when authorized.
- Avoid avatar stacks, activity feed events, or microcopy that could indirectly reveal voter identity.

## 6.6 Ballot review dock

The dock is a sticky glass capsule on desktop and a bottom review bar/sheet on mobile.

### Collapsed state

- Remaining Stars: `3 / 5`.
- Compact progress visualization.
- Count of viewed candidates: `14 / 18 sudah dilihat`.
- Primary action: `Tinjau suara` or `Simpan perubahan` depending on state.

### Expanded state

- List of candidates receiving Stars and the amount assigned to each.
- Direct remove/edit controls.
- Unviewed candidate warning with direct navigation.
- Unused Stars reminder that is informative, not coercive.
- Clear distinction between saved draft ballot and submitted/current ballot.

### Review rules

- The system may remind users about unspent Stars but must allow intentional non-use.
- Before final confirmation, highlight unviewed candidates and explain that submission is still allowed.
- Never require a Star for every candidate.
- Changing the ballot during Voting should update the review dock immediately.

## 6.7 Disqualification during Voting

- A disqualified candidate becomes visibly unavailable but remains represented in the user's ballot history if needed for clarity.
- Stars previously assigned to the disqualified submission are returned automatically.
- Show a clear notification: which submission became unavailable, how many Stars were returned, and that the member may reallocate them.
- The quick index marks the candidate as unavailable.
- The returned Stars trigger a reminder in the ballot dock without forcing immediate action.

## 6.8 Voting completion and ties

- Quorum status, when enabled, is displayed as challenge-level information rather than candidate-level pressure.
- If no quorum is configured, do not show an empty or misleading quorum meter.
- Top-three vote results may be highlighted only after the voting result is finalized.
- A tie state should not visually imply a winner. Show `Hasil seri` and the next configured resolution path.
- If a second vote phase is opened, clearly label it as `Voting penentuan hasil seri` and show only eligible tied candidates.
- A further tie resolved manually should be described as an admin/moderator decision without inventing an in-system judging score.

## 7. Challenge Lifecycle and Winner Systems

The challenge may enable community vote, jury selection, or both.

## 7.1 Lifecycle presentation

Use a stage progression component that can represent:

- Draft
- Scheduled
- Submission Open
- Submission Closed / Preparation
- Voting
- Tiebreak Voting, when needed
- Jury Selection, when enabled
- Paused
- Cancelled
- Finished

The component should distinguish:

- Completed stages
- Current stage
- Upcoming stages
- Exceptional state such as Paused or Cancelled

All displayed dates use explicit WITA formatting, for example `18 Agu 2026, 23.59 WITA`. Countdown timers are supporting information; the authoritative absolute deadline must remain visible.

## 7.2 Challenge visibility

- Visibility is independent from lifecycle status.
- Paused, Cancelled, and Finished challenges may be hidden from members when configured.
- Admin views must display hidden-state indicators explicitly.
- Do not use an Archived status. Use the visibility flag and lifecycle state separately.

## 7.3 Vote winners

- Vote winners are displayed by rank after finalization.
- Highlight the top three with restrained gold hierarchy: first, second, and third should remain visually related rather than using unrelated medal colors.
- Lower vote ranks remain accessible without competing with the top three.
- `vote_rank` is separate from jury winner selection.

## 7.4 Jury-selected winners

- Jury selection has no rank unless the challenge's optional winner category communicates one.
- The challenge configuration determines the number of jury winner slots and optional categories.
- If a slot has no category, label it as a global jury winner.
- Any assigned juror has permission to set all winner slots; selection is shared challenge state, not a separate ballot per juror.
- Display who last modified each slot and when, using JetBrains Mono for the WITA timestamp.
- Use optimistic locking or conflict feedback so one juror does not unknowingly overwrite another juror's recent change.
- Jurors are challenge-scoped permissions, not a global role.
- Moderators or ordinary members may be assigned as jurors.

## 7.5 Independence of winner systems

- Community vote results and jury winners are visually separated into two labeled sections.
- If both systems are enabled, do not imply that the jury validates or overrides the community ranking.
- Jury winner selection must respect the configured rule that a community vote winner cannot also occupy a jury winner slot.
- An ineligible vote winner should remain visible in comparison but have a disabled selection action and clear explanation.
- Example: community vote enabled plus two jury winner slots results in one ranked vote-result section and two category/global jury winner entries.

## 8. Key Screen Direction

## 8.1 Guest landing page

- Start with one strong artwork or rotating curated feature, not a dense product explanation.
- Communicate community identity, active challenge, featured artist, and gallery access.
- Guest CTA should be invitation-aware: registration requires a valid invitation token.
- Do not show account-state language that implies an anonymous guest session exists.
- Public images are limited-resolution watermarked derivatives.

## 8.2 Member gallery and activity

- Gallery discovery remains image-dominant.
- Activity feed should be concise and grouped; avoid turning the home screen into social-media noise.
- Commission openings, new artworks, and challenge state changes may appear as quiet timeline entries.
- Personal or sensitive voting actions never appear in the activity feed.

## 8.3 Artist profile and commission hub

- Hero area: featured artwork, avatar, artist name, discipline, location if provided, and commission status.
- Commission status is immediately visible: `Open`, `Waitlist`, or `Closed`.
- Service cards include thumbnail, service name, price starting point or range, turnaround, and order action.
- Scope information uses a clear expandable section titled in understandable Bahasa Indonesia, such as `Cakupan pesanan`, not unexplained jargon.
- WhatsApp remains the primary direct-order gateway where configured.
- Do not make the commission page look like an e-commerce checkout because payment and escrow are outside the platform.

## 8.4 Challenge detail page

- Hero region contains banner, title, status, authoritative WITA deadline, enabled winner systems, and primary member action.
- Rules and optional template kit are clear but visually secondary.
- The page changes primary emphasis by lifecycle stage: submit during Submission Open, vote during Voting, results after Finished.
- The voting interface should not appear before Voting starts.

## 8.5 Submission editor

- Separate draft-saving from final submission state.
- Show accepted image, GIF, and video formats and the applicable file-size limit before upload.
- Static image limit and GIF/video maximum of 50 MB should be explicit.
- Show progress, processing, derivative generation, and failure states.
- Before the deadline, clearly state that the member may revise the file.
- After the deadline, use a read-only presentation rather than leaving disabled form controls everywhere.

## 8.6 Admin dashboard

- Prioritize current operational tasks: challenges requiring action, invitation management, moderation issues, spotlight reminder, and storage/processing failures.
- Keep analytics compact and secondary.
- Admin tables should be readable and operational, not decorated with amber in every cell.
- Destructive and irreversible actions require confirmation and clear consequence text.

## 9. Responsive Behavior

### Mobile

- Artwork remains first in reading order.
- Minimum touch target: 44×44px.
- Voting controls and the bottom ballot dock must not overlap mobile navigation or browser safe areas.
- Use bottom sheets for filters, metadata, and ballot review.
- Focus deck supports swipe but always includes visible previous/next controls.
- Comparison switches to vertical or A/B toggle mode.
- Avoid mandatory hover interactions.

### Tablet

- Support two-column voting grid and split lightbox when width permits.
- Sticky side controls may become a top or bottom capsule depending on orientation.

### Desktop

- Use whitespace and larger art canvases rather than filling every area with panels.
- Persistent side panels are acceptable for comments, jury comparison, and admin navigation.
- Keyboard navigation is a first-class interaction for focus deck, lightbox, and ballot review.

## 10. Accessibility Requirements

- Meet WCAG 2.1 AA contrast for text and essential controls.
- Every interactive element must have a visible keyboard focus state.
- Do not communicate status through color alone.
- Icon-only buttons require accessible labels and visible tooltips.
- Modal focus must be trapped and returned to the triggering element when closed.
- Announce Star changes, returned Stars, upload completion, and ballot save state with an appropriate live region.
- Provide pause controls for motion media and respect reduced-motion preferences.
- Artwork alt text should describe meaningful visual content where supplied; administrative thumbnails may use concise titles when the visual itself is not the task.
- Do not use drag-only or swipe-only interactions.

## 12. Tailwind and shadcn Implementation Contract

### Tailwind CSS v4

- Define semantic CSS-first tokens instead of scattering literal hex values through components.
- Components consume names such as `bg-canvas`, `bg-surface-1`, `text-primary`, `text-muted`, `border-subtle`, and `text-accent`.
- Preserve semantic token names if light mode is introduced; only token values change.
- Add dedicated tokens for artwork canvas, glass fill, focus ring, and semantic status states.
- Prefer semantic utilities such as `bg-background`, `bg-card`, `text-foreground`, and `border-border` when they map cleanly to shadcn conventions; introduce clearer art-specific tokens such as `bg-artwork-canvas` and `bg-glass` where the generic names are insufficient.
- Keep raw palette tokens and semantic role tokens separate. Components should consume semantic roles so future light mode changes do not require component rewrites.

### shadcn/ui

Recommended primitives:

- Dialog for confirmation and modal details.
- Sheet/Drawer for mobile metadata, filters, scope details, and ballot review.
- Tooltip for icon-only controls.
- Tabs only where content truly represents peer views, such as Grid and Focus.
- Dropdown Menu for secondary actions.
- Alert Dialog for destructive or irreversible actions.
- Toast/Sonner for temporary confirmation.
- Progress for uploads and candidate-view completion.
- Command-style searchable index for fast candidate navigation when submissions are numerous.

Restyle each primitive using the atelier tokens. Default bright shadcn backgrounds, heavy ring styles, and generic rounded cards should not remain unchanged.

Because shadcn/ui places component source code in the application, project-specific changes are expected. Keep the accessible behavior, data attributes, keyboard interactions, and component API stable while adapting colors, radii, spacing, typography, and motion. When adding or overwriting components through the CLI, review the generated diff so custom atelier styling is not unintentionally replaced.

### Responsibility boundary

| Concern | Owner |
|---|---|
| Design tokens and theme variables | Tailwind CSS v4 + global CSS |
| Layout and responsive composition | Tailwind utilities and container queries |
| Accessible primitive behavior | shadcn/ui and its underlying primitives |
| Product-specific composition | Application components |
| Icons | Lucide |
| Complex artwork interactions | Purpose-built viewer/media components styled with Tailwind tokens |
| Server permissions and voting rules | Backend; the frontend only represents authorized state |

### Lucide

- Import icons individually.
- Use consistent sizes and stroke treatment.
- Do not mix Lucide with emoji or text-character substitutes for functional controls.

## 13. Anti-Patterns

Do not implement the following:

- A bright amber border around every card.
- Multiple competing amber buttons in one region.
- Generic SaaS bento grids used solely for decoration.
- Masonry layout in fairness-sensitive challenge voting.
- Random candidate reshuffling on every render or refresh.
- Hidden artist names during voting; only voter identity is anonymous.
- Avatar stacks that reveal or imply who voted.
- Cropped artwork in jury comparison or focus evaluation.
- Tiny icon-only controls without labels or tooltips.
- Excessive glass blur that reduces text clarity or mobile performance.
- Pure black backgrounds everywhere; preserve layered warm obsidian depth.
- Default shadcn styling without visual adaptation.
- Long technical English microcopy where natural Bahasa Indonesia is clearer.
- Scroll behavior that forcibly skips content or makes mobile navigation unpredictable.
- Auto-playing motion with sound.
- Treating anti-right-click as complete artwork security.

## 14. Definition of Done for Frontend Review

A screen is visually complete when all applicable conditions are true:

- Artwork is the strongest visual element.
- The screen has one clear primary action.
- Amber is used intentionally and sparingly.
- Text hierarchy is understandable without relying on card borders.
- Dark surfaces are layered and readable rather than flat black.
- Loading, empty, success, error, disabled, and permission-denied states exist.
- Keyboard focus is visible and logical.
- Mobile touch targets are at least 44px.
- Critical actions and states do not depend on hover.
- WITA deadlines show an absolute time, not only a countdown.
- Public and member artwork quality/access states are accurately represented.
- Voting cards receive equal visual prominence.
- Candidate order is stable for the same voter during the round.
- The quick index distinguishes viewed, unviewed, allocated, and unavailable candidates.
- The ballot dock shows remaining Stars and allows intentional unused Stars.
- Voter identities are not exposed to members.
- The grid, focus deck, and comparison mode preserve ballot state.
- Jury and community vote winners are presented as independent systems.
- Reduced-motion behavior is available.
- No component ships with visually unmodified default-library styling.
